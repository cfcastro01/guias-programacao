Aula 1

O que é desenvolvimento de software

Objetivo da aula

Entender o que é software, conhecer as principais etapas de seu desenvolvimento e reconhecer como a IA pode ajudar sem substituir o entendimento e a validação humana.

O que é software?

Software é um conjunto de instruções e regras executadas por um computador para realizar uma tarefa. Um site, um aplicativo, um sistema interno de empresa, uma API e o sistema de um caixa eletrônico são exemplos de software.

O software não é apenas uma tela ou um trecho de código isolado. Ele pode incluir diferentes partes, como interface, regras, dados e integrações. Já seu desenvolvimento envolve entender o problema, tomar decisões e testar o resultado.

O que significa desenvolver software?

Desenvolver software é criar e cuidar de uma solução digital. Esse trabalho costuma passar por um fluxo simples:

  1. Problema: identificar a necessidade.
  2. Entendimento: descobrir quem usará a solução e o que ela precisa fazer.
  3. Planejamento: escolher uma forma simples de construir.
  4. Implementação: criar a solução, inclusive seu código.
  5. Testes: verificar se tudo funciona como esperado.
  6. Correções: ajustar erros e pontos pouco claros.
  7. Publicação: disponibilizar o software para uso.
  8. Manutenção: acompanhar, corrigir e melhorar depois da publicação.

Na prática, essas etapas podem se repetir. Um teste pode revelar que o entendimento inicial precisa ser revisto.

Como ler em português

“Desenvolver software é transformar um problema ou uma necessidade em uma solução digital que funcione e possa ser mantida.”

Pense primeiro na necessidade e depois na tecnologia. O código é uma parte da solução, não o objetivo final.

Exemplo prático

Imagine que precisamos criar uma página para uma pessoa registrar seus gastos. Antes de considerá-la pronta, seria necessário:

  1. entender quais gastos precisam ser registrados;
  2. definir campos como descrição, valor e data;
  3. criar uma interface fácil de usar;
  4. decidir onde os dados serão salvos;
  5. testar valores e situações diferentes;
  6. corrigir os problemas encontrados;
  7. publicar a página e acompanhar seu uso.

Perceba que escrever o código acontece dentro desse processo, mas não representa o processo inteiro.

Como isso aparece em um projeto real

Em um projeto real, diferentes pessoas podem participar das etapas. Alguém esclarece a necessidade, outra pessoa planeja a interface, desenvolvedores implementam e testadores ajudam a encontrar problemas. Mesmo quando uma pessoa faz tudo, as responsabilidades continuam existindo.

Como isso muda quando usamos IA

Ferramentas como Codex e Claude Code podem analisar código, sugerir soluções, escrever trechos, criar testes, encontrar erros e ajudar na documentação. Isso pode tornar várias etapas mais rápidas.

Ainda cabe à pessoa responsável pelo projeto:

  • entender qual problema deve ser resolvido;
  • decidir o que realmente precisa ser construído;
  • fornecer contexto e critérios claros para a IA;
  • testar e validar o resultado;
  • assumir a responsabilidade pelo software entregue.

A IA pode ajudar a produzir uma solução, mas não garante que ela esteja correta, segura ou adequada ao problema.

Riscos ou erros comuns

  • Achar que desenvolver software é apenas escrever código.
  • Começar a implementar antes de entender o problema.
  • Aceitar código produzido por IA sem testar.
  • Criar uma solução mais complexa do que o necessário.

Perguntas úteis para fazer a um desenvolvedor

  • Qual problema esta funcionalidade precisa resolver?
  • Como saberemos que ela está funcionando corretamente?
  • O que ainda precisará ser mantido depois da publicação?

Como explicar esse assunto em uma entrevista

Pergunta: O que é desenvolvimento de software?

Resposta possível: “É o processo de transformar uma necessidade em uma solução digital. Isso envolve entender o problema, planejar, implementar, testar, publicar e manter o software.”

Você não precisa decorar a frase. O importante é explicar que o trabalho começa no problema e continua depois que o código é publicado.

Resumo

  • Software é um conjunto de instruções e regras que permite a um computador realizar tarefas.
  • Código é uma parte do software, não o trabalho inteiro.
  • Desenvolver inclui entender, planejar, implementar, testar, publicar e manter.
  • A IA ajuda em várias etapas, mas o resultado precisa ser validado.

Exercício de reforço

Uma empresa quer criar uma página para funcionários registrarem pedidos de férias. Qual opção descreve melhor o que deve acontecer antes de considerar a funcionalidade pronta?

Sua escolha fica salva, mas não altera a conclusão da aula.

Resposta comentada

A resposta correta é a opção C.

Primeiro é preciso entender regras como antecedência, aprovação e datas permitidas. Depois, a equipe pode planejar os campos e o fluxo, implementar, testar situações reais, corrigir problemas e só então publicar.

A IA pode ajudar no planejamento, no código e nos testes, mas não deve decidir sozinha as regras da empresa nem substituir a validação do resultado.

Conclusão da aula

Você pode desmarcar esta opção quando quiser.

Aula 2

Frontend, backend e banco de dados

Objetivo da aula

Explicar o papel de cada parte, como elas trabalham juntas e onde a IA pode ajudar no desenvolvimento.

Frontend: a parte com a qual a pessoa interage

Frontend inclui telas, botões, formulários, menus e mensagens. Essa parte visível e interativa também é chamada de interface.

Não é só aparência: também há lógica no navegador ou aplicativo, como abrir um menu e avisar que um campo está vazio.

Backend: regras e operações por trás da interface

Backend verifica informações e permissões, processa solicitações e coordena a busca ou o salvamento de dados. Por exemplo, confere se uma pessoa pode registrar determinada despesa.

Banco de dados: informações organizadas

É onde o sistema organiza e guarda informações, como usuários, pedidos, produtos e despesas. Quando uma informação precisa continuar disponível depois que a página é fechada, ela pode ser armazenada em um banco de dados.

Como ler em português

  • Frontend: parte visível e interativa do sistema.
  • Backend: parte que processa regras e coordena o que acontece por trás da interface.
  • Banco de dados: lugar onde o sistema organiza e guarda informações.

Como as três partes trabalham juntas

Imagine uma pessoa registrando uma despesa:

Usuário
   ↓
Frontend
   ↓
Backend
   ↓
Banco de dados
  1. O frontend recebe a descrição e o valor digitados.
  2. O backend verifica as regras e processa o pedido de registro.
  3. O banco de dados armazena a despesa.
  4. Depois, o backend pode buscar a despesa no banco.
  5. O frontend apresenta o resultado à pessoa.

Esse é um modelo simplificado. Sistemas reais podem variar, e nem todo site precisa dessas três partes.

Exemplo prático: cadastrar um novo usuário

  • Frontend: exibe o formulário, coleta os dados e mostra mensagens.
  • Backend: valida as regras, verifica se o cadastro pode ser feito e processa a operação.
  • Banco de dados: guarda os dados do usuário.

Como isso aparece em um projeto real

As responsabilidades podem estar em arquivos diferentes. No frontend, HTML organiza o conteúdo, CSS define a aparência e JavaScript cria comportamentos. O backend tem código para executar regras. No banco de dados, as informações podem ser organizadas em tabelas, com linhas e colunas.

As tecnologias variam. Primeiro, procure entender a responsabilidade de cada parte.

Como isso muda quando usamos IA

Ferramentas de IA podem criar interfaces, escrever regras de backend, preparar buscas e alterações no banco, analisar as conexões entre essas partes e encontrar erros.

A IA precisa receber contexto suficiente para saber em qual parte do sistema deve mexer. Pedir uma mudança na cor de um botão não deveria levar automaticamente a mudanças no banco. Explique o problema, limite o pedido e teste o resultado.

Erros comuns

  • Achar que frontend é só aparência ou que backend é o próprio banco.
  • Confiar apenas no frontend para regras importantes: dados também precisam ser verificados no backend quando ele existe.
  • Alterar dados sem entender o impacto ou pedir à IA uma correção sem explicar o problema.

Como explicar esse assunto em uma entrevista

Pergunta: Qual é a diferença entre frontend, backend e banco de dados?

Resposta possível: “Frontend é a parte com a qual o usuário interage. Backend processa regras e operações. Banco de dados guarda as informações que precisam ser mantidas. As três partes normalmente trabalham juntas.”

Exercício de reforço

Em um cadastro de produtos, classifique a responsabilidade principal de cada item antes de escolher a combinação:

  1. Exibir o formulário de cadastro.
  2. Verificar se a pessoa tem permissão para cadastrar.
  3. Guardar nome e preço do produto.
  4. Mostrar uma mensagem de sucesso.
  5. Aplicar uma regra que impede o registro de preço negativo.

Qual combinação corresponde aos itens A, B, C, D e E, nessa ordem?

Sua escolha fica salva, mas não altera a conclusão da aula.

Resposta comentada

A combinação correta é a opção 3.

  • A e D — Frontend: o formulário e a mensagem são partes da interação com a pessoa.
  • B e E — Backend: permissão e preço permitido são regras que precisam ser verificadas antes de aceitar o cadastro.
  • C — Banco de dados: guardar nome e preço mantém o produto disponível para consultas posteriores.

O frontend também pode avisar sobre um preço negativo, mas esse aviso não substitui a verificação da regra no backend.

Conclusão da aula

Você pode desmarcar esta opção quando quiser.

Aula 3

Cliente e servidor

Objetivo da aula

Identificar quem solicita e quem responde em uma comunicação, sem confundir esses papéis com frontend e backend.

O que é cliente?

Cliente é a parte que solicita algo. O navegador ou aplicativo costuma atuar como cliente: por exemplo, o navegador pede uma página para mostrar à pessoa.

Aqui, cliente é um papel do programa na comunicação, não a pessoa que compra um produto.

O que é servidor?

Servidor é a parte que recebe a solicitação, processa o pedido e devolve uma resposta. Essa resposta pode trazer uma página, informações ou uma mensagem de erro.

Esse trabalho é feito por um programa. Ele pode funcionar no seu computador ou em outras máquinas; não precisa corresponder a um único computador físico.

Como ler em português

  • Cliente: quem pede.
  • Solicitação: o pedido enviado.
  • Servidor: quem recebe o pedido e responde.
  • Resposta: o retorno do pedido.

Fluxo simples

Cliente
   ↓
Solicitação
   ↓
Servidor
   ↓
Resposta
   ↓
Cliente

Cliente e servidor trocam mensagens seguindo regras de comunicação. Por enquanto, acompanhe apenas o caminho do pedido e da resposta.

Exemplo prático: abrir uma página de produtos

  1. O navegador solicita a página de produtos.
  2. O servidor recebe o pedido.
  3. O servidor busca as informações necessárias e prepara o resultado.
  4. O servidor envia a resposta ao navegador.
  5. O navegador interpreta a resposta e mostra a página.

Em um projeto real, acompanhar esse caminho ajuda a investigar uma página que não carrega: o pedido foi enviado? Houve resposta? O navegador conseguiu mostrá-la?

Cliente/servidor e frontend/backend

Cliente e servidor descrevem quem solicita e quem responde. Frontend e backend descrevem responsabilidades da aplicação: interação com a pessoa e processamento de regras.

Frequentemente, o frontend funciona no cliente e o backend no servidor. Mas os termos não são sinônimos: um backend também pode atuar como cliente ao pedir informações a outro servidor.

Como isso muda quando usamos IA

A IA pode ajudar a gerar código e investigar erros dos dois lados. Para isso, precisa saber se o problema está no cliente, no servidor ou na comunicação entre eles.

Descreva a ação, o resultado esperado e o que aconteceu. Por exemplo: “O pedido de produtos recebe uma resposta, mas o navegador não mostra a lista.” Confira a investigação e teste a correção sugerida.

Erros comuns

  • Achar que servidor é sempre um único computador físico.
  • Confundir servidor com banco de dados: receber e responder pedidos é diferente de organizar e guardar informações.
  • Usar cliente/servidor como sinônimos de frontend/backend.

Como explicar esse assunto em uma entrevista

Pergunta: Qual é a diferença entre cliente e servidor?

Resposta possível: “Cliente é quem faz uma solicitação, como um navegador pedindo uma página. Servidor é quem recebe esse pedido, processa e devolve uma resposta.”

Exercício de reforço

Um aplicativo de clima solicita a previsão para uma cidade. Um serviço recebe o pedido e devolve a previsão. Quem atua como cliente e quem atua como servidor nessa troca?

Sua escolha fica salva, mas não altera a conclusão da aula.

Resposta comentada

A resposta correta é a opção B.

O aplicativo atua como cliente porque faz o pedido da previsão. O serviço atua como servidor porque recebe esse pedido, processa e envia uma resposta. Os papéis são identificados pelo que cada parte faz nessa troca.

Conclusão da aula

Você pode desmarcar esta opção quando quiser.

Aula 4

APIs, HTTP e JSON

Objetivo da aula

Entender o que são API, HTTP e JSON e reconhecer o papel de cada um em uma troca de informações entre cliente e servidor.

O que é uma API?

API vem de Application Programming Interface, ou interface de programação de aplicações. É uma forma definida de um programa usar recursos de outro, com regras sobre o que pode pedir e o que pode receber.

Uma API de clima, por exemplo, pode permitir consultar a previsão de uma cidade. Sua documentação explica como fazer o pedido e quais informações aparecem na resposta.

Existem APIs em diferentes contextos. Nesta aula, vamos olhar para uma API web, acessada pela comunicação entre cliente e servidor.

O que é HTTP?

HTTP vem de Hypertext Transfer Protocol, ou protocolo de transferência de hipertexto. Um protocolo é um conjunto de regras de comunicação. HTTP define como cliente e servidor trocam pedidos e respostas na web.

O pedido informa, por exemplo, o endereço do recurso desejado. A resposta inclui um código de status, que indica o resultado: 200 costuma indicar sucesso, enquanto 404 indica que o recurso não foi encontrado.

Você também verá HTTPS: é HTTP com proteção da comunicação por criptografia, que ajuda a impedir a leitura e a alteração das mensagens por terceiros durante o caminho.

O que é JSON?

JSON vem de JavaScript Object Notation, ou notação de objetos JavaScript. É um formato de texto usado para organizar e trocar dados. Apesar do nome, programas escritos em várias linguagens conseguem usá-lo.

Em um objeto JSON, cada nome aparece entre aspas duplas e é separado de seu valor por dois-pontos. Os pares ficam entre chaves e são separados por vírgulas.

{
  "cidade": "Recife",
  "temperatura": 28,
  "chovendo": false
}

"Recife" é um texto, 28 é um número e false é um valor booleano: significa falso. Neste exemplo, a temperatura está em graus Celsius e não está chovendo.

JSON representa dados; ele não é um programa que executa ações.

Como ler em português

  • API: a forma definida para um programa pedir dados ou recursos a outro.
  • HTTP: as regras usadas para enviar o pedido e receber a resposta na web.
  • JSON: o formato de texto que organiza os dados trocados.
  • "cidade": "Recife": “o campo cidade tem o valor Recife”.
  • "chovendo": false: “é falso que está chovendo”.

Exemplo prático: consultar o clima

Imagine uma API fictícia que oferece a consulta /clima?cidade=Recife. Esse caminho identifica a consulta de clima, e a parte depois de ? informa a cidade desejada.

  1. O aplicativo, como cliente, envia um pedido HTTP para esse endereço no servidor da API.
  2. O servidor consulta as informações de clima e prepara a resposta.
  3. A resposta HTTP chega com status 200 e um corpo, a parte que contém os dados, em JSON como o exemplo acima.
  4. O aplicativo interpreta os dados e mostra “Recife: 28 °C, sem chuva”.

A API define a consulta disponível; HTTP organiza a troca de mensagens; JSON organiza os dados da resposta. Este exemplo serve para leitura: não há um serviço de clima conectado a esta página.

Nem toda API usa HTTP, e nem toda resposta HTTP usa JSON: uma resposta também pode trazer HTML, uma imagem ou outro conteúdo.

Como isso aparece em um projeto real

Um aplicativo pode usar uma API para buscar produtos, consultar entregas ou mostrar o clima. Para investigar um problema, confira qual consulta foi feita, qual status voltou e se os dados têm os campos esperados.

Receber status 200 não garante que a tela esteja correta: o aplicativo ainda precisa interpretar e apresentar os dados.

Como isso muda quando usamos IA

A IA pode ajudar a escrever uma consulta e interpretar a resposta. Forneça a documentação da API e um exemplo de JSON sem dados pessoais ou segredos, em vez de pedir que ela adivinhe endereços e campos.

Um pedido possível é: “Com base nesta documentação e nesta resposta de exemplo, explique como mostrar a cidade e a temperatura. Aponte o que conferir se a consulta falhar.” Compare a sugestão com a documentação e valide o resultado.

Erros comuns

  • Tratar API, HTTP e JSON como sinônimos: cada um tem um papel diferente.
  • Achar que JSON executa código ou funciona apenas com JavaScript.
  • Escrever nomes de campos com aspas simples ou deixar uma vírgula depois do último par: isso não é JSON válido.
  • Supor que a API sempre responde com sucesso ou sempre devolve os mesmos dados.

Perguntas úteis para fazer a um desenvolvedor

  • Onde está a documentação dessa API e qual consulta devemos usar?
  • Quais campos a resposta traz e o que significa cada um?
  • O que o aplicativo deve mostrar se a consulta falhar ou não houver dados?

Como explicar esse assunto em uma entrevista

Pergunta: Como API, HTTP e JSON se relacionam?

Resposta possível: “Uma API define como um programa usa recursos de outro. Em uma API web, HTTP pode ser usado para trocar pedidos e respostas, e JSON pode organizar os dados dessas mensagens.”

Resumo

API define o acesso aos recursos, HTTP define a comunicação na web e JSON é um formato para representar os dados. Eles podem trabalhar juntos, mas não são a mesma coisa.

Exercício de reforço

Um aplicativo de entregas usa uma consulta documentada para buscar um pedido. Ele envia uma mensagem HTTP e recebe {"pedido": 42, "status": "em rota"}. Qual alternativa identifica corretamente os três conceitos?

Sua escolha fica salva, mas não altera a conclusão da aula.

Resposta comentada

A resposta correta é a opção C.

A consulta documentada faz parte da API. O pedido e a resposta seguem HTTP. O texto com os campos pedido e status está em JSON e informa que o pedido 42 está em rota.

O campo status desse JSON descreve a entrega. Ele não é o código de status HTTP, que informa o resultado da comunicação.

Conclusão da aula

Você pode desmarcar esta opção quando quiser.

Aula 5

Ambiente local, staging e produção

Objetivo da aula

Distinguir ambiente local, staging e produção, entender por que são separados e reconhecer o risco de experimentar alterações no sistema usado pelas pessoas.

O que é um ambiente?

Ambiente é o conjunto de condições em que um software funciona: sua versão, suas configurações, seus dados e os serviços aos quais se conecta.

O mesmo sistema pode funcionar em ambientes separados. Assim, a equipe consegue desenvolver e conferir mudanças antes de colocá-las à disposição dos usuários.

Ambiente local: desenvolver e experimentar

É o ambiente preparado no computador de quem desenvolve. Nele, a pessoa altera arquivos e verifica o resultado enquanto trabalha.

Ao abrir este guia em http://localhost:8000/, você acessa um servidor no próprio computador. localhost é o nome usado para se referir à própria máquina.

Estar no ambiente local não garante que tudo esteja isolado: se o programa estiver configurado para usar um serviço ou dados de produção, suas ações ainda podem afetar o sistema real.

Staging: conferir antes de publicar

Staging é um ambiente de validação, também chamado de homologação. Ele busca se aproximar das condições de produção para que a equipe confira uma versão antes de liberá-la aos usuários.

Por exemplo, outras pessoas podem testar um formulário e verificar se as partes do sistema funcionam juntas, usando dados de teste e serviços separados dos reais.

Staging ajuda a encontrar problemas, mas não garante que nenhum erro aparecerá em produção. Os ambientes podem ter diferenças de configuração, dados e quantidade de acessos.

Produção: o sistema em uso real

É o ambiente que atende os usuários de verdade. Em uma loja, é onde as pessoas consultam produtos e fazem pedidos reais.

Testar uma mudança diretamente ali pode interromper uma compra, gravar dados incorretos ou enviar mensagens indevidas. O impacto deixa de ficar restrito ao trabalho da equipe e chega às pessoas que dependem do sistema.

Como ler em português

  • Ambiente: onde e em quais condições o sistema funciona.
  • Local: “vou desenvolver e conferir no meu computador”.
  • Staging ou homologação: “vamos validar esta versão antes de liberar aos usuários”.
  • Produção: “esta é a versão usada pelas pessoas no dia a dia”.
  • Local → staging → produção: “desenvolver, validar e então liberar para uso real”.

Exemplo prático: melhorar um formulário de contato

Uma equipe quer mostrar uma mensagem mais clara quando alguém deixa o campo de e-mail vazio.

  1. Local: a pessoa desenvolve a mensagem e testa o formulário com o campo vazio e preenchido, sem enviar mensagens reais.
  2. Staging: a equipe confere a mesma mudança em um ambiente separado, com contatos fictícios e envio direcionado a uma caixa de teste. Verifica também se o formulário continua funcionando no celular e por teclado.
  3. Produção: depois da validação e da revisão, a versão é liberada para os usuários. A equipe acompanha se o formulário continua funcionando como esperado.

Se a validação em staging revelar um problema, a mudança volta para correção e novos testes antes de seguir. Esse fluxo reduz riscos; não é uma garantia de ausência de falhas.

Como isso aparece em um projeto real

Antes de alterar ou testar algo, confirme o ambiente, os dados usados e os serviços conectados. Um endereço com a palavra “teste” não comprova, sozinho, que tudo está separado de produção.

A organização varia entre projetos: um site pequeno pode começar apenas com local e produção. O importante é saber quem pode ser afetado e como validar a mudança antes de liberá-la.

Como isso muda quando usamos IA

Ao pedir ajuda a um agente de IA, informe em qual ambiente ele pode trabalhar, o que deve alterar e como conferir o resultado. Revise as mudanças e os testes antes de autorizar uma publicação.

Um pedido possível é: “Ajuste a mensagem do formulário no ambiente local. Use dados fictícios, confira o campo vazio e preenchido e pare antes de publicar.” A IA não deve presumir que pode testar em produção só porque tem acesso a ela.

Riscos ou erros comuns

  • Experimentar em produção porque a alteração parece pequena: um detalhe pode impedir uma ação importante.
  • Achar que funcionar localmente garante o mesmo resultado nos outros ambientes.
  • Usar dados pessoais reais ou serviços de produção em testes sem conferir as consequências.
  • Tratar a aprovação em staging como motivo para dispensar o acompanhamento após a publicação.

Perguntas úteis para fazer a um desenvolvedor

  • Em qual ambiente estamos e quem pode ser afetado por esta ação?
  • Os dados e os serviços usados nos testes estão separados de produção?
  • O que precisa ser validado antes da liberação e como agir se houver um problema depois?

Como explicar esse assunto em uma entrevista

Pergunta: Qual é a diferença entre local, staging e produção?

Resposta possível: “Local é onde desenvolvemos no nosso computador. Staging é um ambiente separado para validar uma versão em condições próximas às de produção. Produção atende os usuários reais, por isso experimentar diretamente ali pode afetar pessoas e dados.”

Resumo

Local permite desenvolver, staging ajuda a validar e produção atende o uso real. Separar esses ambientes reduz o risco de uma experiência ou um erro atingir os usuários.

Aula 6

Build e deploy

Objetivo da aula

Entender o que são build e deploy e distinguir preparar uma versão de disponibilizá-la em um ambiente.

O que é build?

Build é o processo de preparar os arquivos de uma versão do software para uso. Dependendo do projeto, ele pode transformar código, juntar arquivos ou reduzir seu tamanho.

Por exemplo, um projeto pode reunir vários arquivos JavaScript em um arquivo menor para o navegador carregar. O conjunto de arquivos gerado também costuma ser chamado de build.

Preparar esses arquivos não significa publicá-los. Eles podem continuar apenas no computador de quem desenvolve.

O que é deploy?

Deploy é o processo de colocar uma versão do software em um ambiente e disponibilizá-la para uso ali. Em um site, isso pode envolver enviar os arquivos ao serviço que entrega as páginas aos visitantes.

Um deploy pode ser feito em staging para validação ou em produção para atender os usuários reais. Portanto, fazer deploy não significa necessariamente publicar em produção.

Nem todo projeto precisa de um build separado

Um site simples com HTML, CSS e JavaScript puro, como este guia, pode usar os próprios arquivos escritos pela pessoa, sem uma transformação antes de publicá-los.

Nesse caso, o fluxo pode ser alteração → validação → deploy. A ausência de um build separado não elimina a necessidade de revisar e testar os arquivos antes da publicação.

O comando npx serve . -l 8000 permite servir este guia localmente. Ele não cria um build nem publica o site na internet.

Como ler em português

  • Build: “preparar os arquivos da versão para uso”.
  • Validação: “conferir se essa versão atende ao esperado”.
  • Deploy: “disponibilizar a versão no ambiente escolhido”.
  • Build concluído: “os arquivos foram gerados; ainda preciso conferir o resultado”.
  • Deploy em produção: “a versão foi disponibilizada no ambiente usado pelas pessoas”.

Exemplo prático: atualizar um botão

Imagine um site que tem uma etapa de build. A equipe quer mudar o texto de um botão de “Enviar” para “Enviar mensagem”.

  1. Alteração: a pessoa edita o texto no arquivo de origem, onde a equipe mantém o código do site.
  2. Build: o processo do projeto gera os arquivos da nova versão, já com o texto atualizado.
  3. Validação: a equipe abre a versão preparada em um ambiente de teste, confere o texto e verifica se o botão continua funcionando, inclusive por teclado.
  4. Deploy: após revisão e autorização, a versão validada é disponibilizada em produção. A equipe confere o resultado no site publicado.

Alteração → build → validação → deploy. Esse fluxo resume a publicação neste exemplo. Se a validação precisar de staging, há também um deploy nesse ambiente antes de conferir a versão ali.

Se um problema exigir nova alteração nos arquivos de origem, é necessário gerar e validar novamente o build antes de publicá-lo. Um build antigo não inclui mudanças feitas depois de sua geração.

Como isso aparece em um projeto real

Antes de publicar, a equipe precisa saber se o projeto exige build, quais arquivos devem ser enviados e em qual ambiente a versão será disponibilizada.

Um build concluído indica que a preparação terminou, mas não comprova que todos os comportamentos estão corretos. Da mesma forma, um deploy concluído não dispensa conferir se o sistema funciona no ambiente de destino.

Como isso muda quando usamos IA

A IA pode ajudar a alterar arquivos, identificar como o projeto prepara uma versão e analisar erros. Ela precisa conhecer as instruções do projeto e os critérios de validação, sem inventar uma etapa de build que não existe.

Um pedido possível é: “Altere o texto do botão, siga a preparação já usada neste projeto e confira o resultado. Informe o que foi validado e pare antes de fazer deploy.” Revise as mudanças antes de autorizar a publicação.

Erros comuns

  • Achar que executar o build já atualiza o site publicado.
  • Publicar arquivos de um build antigo depois de alterar o código.
  • Tratar a conclusão do build como prova de que a versão funciona corretamente.
  • Adicionar ferramentas de build a um projeto simples sem uma necessidade clara.
  • Fazer deploy no ambiente errado por não conferir o destino.

Perguntas úteis para fazer a um desenvolvedor

  • Este projeto precisa de build ou usa diretamente os arquivos de origem?
  • Quais arquivos representam a versão que será publicada?
  • O que foi validado e em qual ambiente será feito o deploy?

Como explicar esse assunto em uma entrevista

Pergunta: Qual é a diferença entre build e deploy?

Resposta possível: “Build prepara os arquivos de uma versão. Deploy disponibiliza essa versão em um ambiente, como staging ou produção. Alguns projetos simples usam seus arquivos diretamente e não precisam de uma etapa de build separada.”

Resumo

Preparar uma versão e publicá-la são ações diferentes. Quando existe build, valide o resultado que será disponibilizado. Quando não existe, valide os próprios arquivos antes do deploy.
